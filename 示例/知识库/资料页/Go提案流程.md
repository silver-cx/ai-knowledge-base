# Go 语言的提案流程

> 最「轻」的一套流程：先用一个简短的 issue 提出，只有需要时才写设计文档。评审会每周开，状态用看板列表示，每一步都公开记录。

## 什么时候看

想要一套轻量的提案流程；同时有很多提案排队、需要管理进度时。

## 要点

- 第一步只需要一个简短的 issue，不需要设计文档；讨论后三选一：接受、拒绝、要求写设计文档。
- 流程的目标：每个提案都得到**公正、及时、有记录**的评估和明确答复；历史提案容易查到，避免重复劳动。
- 评审组每周开会，主要任务是确保「对的人在关注」、推动讨论走向结论，而不是在会上讨论本身。
- 「可能接受 / 可能拒绝」是最后一周的公示期，没有新变化就转为正式决定。
- 无法达成共识时默认拒绝；仍有分歧则逐级上交给架构师组，再到最终仲裁人。

## 逐节

### 流程四步
> 原文：The Proposal Process
- 1 作者提交简短 issue（此时不需要设计文档）。
- 2 讨论，目标是分诊为三种结果之一：接受、拒绝、要求写设计文档。
- 3 需要时，作者写设计文档，回应初步讨论中提出的关注点。
- 4 设计文档的意见收敛后，在 issue 上做最终讨论：接受或拒绝。
- 决定后，实现工作与普通贡献一样推进。

### 目标
> 原文：Goals
- 确保提案得到恰当、公正、及时、有记录的评估，并有明确答复。
- 让过去的提案容易查到，避免重复劳动。
- 需要设计文档时，让贡献者知道怎么写好。

### 范围
> 原文：Scope
- 「值得注意的」改动都应走流程：公开 API 变更、命令行变更、需要兼容开关的可见行为变化、新协议或新算法。
- 拿不准就提——「If in doubt, file a proposal.」
- 内部包、构建基础设施等用户看不到的改动通常不需要。

### 兼容性
> 原文：Compatibility
- 任何提案都不能破坏「Go 1 兼容承诺」：为 1.x 写的程序在后续 1.x 版本上必须继续编译和运行。
- 语言改动的门槛：解决很多人的重要问题、对其他人影响最小、有清晰且被充分理解的方案。

### 设计文档
> 原文：Design Documents
- 并非所有提案都需要设计文档；需要时按模板写，回应初步讨论中的关注点，可以多次修订。
- 新作者可以配一位「牧羊人」协助。
- 每句话单独起一行，便于精确评论、让修改记录更短。
- 文档评审里只讨论文字和流程问题，实质意见回到 issue 上讨论。
- 有经验的提交者如果确定需要设计文档，可以跳过前两步，直接随 issue 一起提交。

### 每周评审
> 原文：Proposal Review
- 评审组约每周开会，确保提案被对的人看到：抄送相关开发者、提出关键问题、催促停滞的讨论、引导走向一致。
- 讨论本身在 issue 上进行，任何人都可以参与；会议纪要公开发布。
- 评审组可以为紧急或无需完整评审的提案开快速通道。

### 状态看板
> 原文：Incoming
- **新进**：先排队，等有精力时再移入「讨论中」——先把在途的提案推到结论，避免「新工作挤占旧工作」导致谁都完不成。
- **讨论中**：每周会上观察是否出现共识，评审组会帮忙复述提案，确认大家在讨论同一件事。
- **可能接受 / 可能拒绝**：认为已有共识时移入，并发评论说明；这是最后一周的意见期。
- **已接受 / 已拒绝**：公示一周无重大变化即转为正式决定；若有重要讨论可再留一周或退回讨论。
- **快速拒绝**：重复（参考既往决定，不轻易重议）、不可行（与核心设计冲突或无法实现）、作者撤回、已过时，可直接拒绝。
- **搁置**：需要等几周以上的信息或修订时移入，并注明在等什么。

### 共识与分歧
> 原文：Consensus and Disagreement
- 流程的目标是及时达成普遍共识；找不到共识时，通常结果是拒绝。
- 例外：大家都同意问题重要，但对选哪个方案没有共识——这时交给架构师组，在 issue 上记录决定和理由。
- 架构师组也无法达成一致时（更少见），由仲裁人决定下一步并记录理由。
