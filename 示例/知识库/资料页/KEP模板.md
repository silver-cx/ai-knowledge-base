# Kubernetes 增强提案（KEP）模板

> 一份为「要上线、要能回滚」的功能设计的提案模板。比其他几份都更重视目标/非目标、测试、分阶段发布和线上可运维性。

## 什么时候看

方案涉及上线、灰度和回滚；想补齐目标与非目标、风险、分阶段上线标准。

## 要点

- 先写摘要和动机，**尽早合并、再逐步补细节**；正在争论的段落用 UNRESOLVED 标记圈出来。
- 动机拆成「目标」和「非目标」，非目标用来收窄讨论。
- 风险要「想得宽」：安全怎么审、体验怎么审、由谁审。
- 发布分 Alpha / Beta / GA 三档，每档有明确的毕业标准；功能、安全、监控、测试要求必须在 Beta 前完成。
- 生产就绪问卷逼作者回答：怎么开关、怎么回滚、看哪些指标决定回滚、出故障怎么排查。

## 逐节

### 使用说明
> 原文：To get started with this template
- 先找负责的兴趣小组（SIG），没有 SIG 认领的 KEP 不应提交。
- 至少先填好摘要和动机——如果事先和 SIG 沟通过，这两节应该很好写。
- 「尽早合并、持续迭代」：别卡在细节上，先把目标对齐、合并，再用后续修改补细节。
- 合并不等于批准；有争议的段落用 `<<[UNRESOLVED]>> … <<[/UNRESOLVED]>>` 标出来。
- 修改要小而单一；不同意已有内容就另开一个修改提议。
- 一个 KEP 对应一个功能的完整生命周期；功能已实现后的大改要开新 KEP。

### 发布核对清单
> 原文：Release Signoff Checklist
- 进入某个版本前必须完成的清单：KEP 状态被批准为可实施、设计细节写清、测试计划到位、毕业标准到位、生产就绪审查完成并批准。
- 还包括：实施历史更新、面向用户的文档、相关讨论和决策链接。
- 清单每次考虑进入新版本时都要重新核对。

### 摘要
> 原文：Summary
- 这一节会被直接拿去做发布说明和路线图，要写给广泛读者看。
- 应该在动手实现之前就能写出来；一个好摘要通常至少一段话。

### 动机
> 原文：Motivation
- 说明为什么重要、对用户有什么好处，可以附用户的经验反馈。
- **目标**：具体想达成什么，怎么判断成功。
- **非目标**：明确不做什么。列非目标能让讨论聚焦、推进更快。

### 提案
> 原文：Proposal
- 写清提议到底是什么、期望结果是什么、怎么衡量成功；但不写 API 设计和实现，那些放到设计细节。
- 用户故事：实现之后用户能做什么，让它「感觉真实」但不陷入细节。
- 注意事项和限制：上面没讲到的重要细节、核心概念之间的关系。

### 风险与应对
> 原文：Risks and Mitigations
- 有哪些风险、怎么缓解，要「想得宽」，包括对整个生态的影响。
- 安全由谁、怎么审；体验由谁、怎么审；建议拉上小组之外的人。

### 设计细节
> 原文：Design Details
- 写到足以让人理解具体改动，可以包含 API 规格或代码片段。
- 「怎么实现」上只要有歧义，就在这里讨论。

### 测试计划
> 原文：Test Plan
- 目标是不接受测试不充分的改进。
- 分单元测试、集成测试、端到端测试分别说明；做不到完整覆盖要解释原因及为什么可以接受。

### 毕业标准
> 原文：Graduation Criteria
- 用 Alpha / Beta / GA 三档定义成熟度，重点写「看哪些信号决定毕业」。
- Alpha：功能藏在开关后面，基础测试完成。
- Beta：收集开发者反馈和调研，功能、安全、监控、测试要求全部完成，已知问题全部解决。
- GA：N 个真实使用案例、N 次安装、给反馈留出时间，Beta 期间发现的问题全部解决。
- GA 标准里**不能**再出现功能、安全、监控、测试要求，这些必须在 Beta 完成。
- Beta 到 GA 通常至少隔两个版本，否则用户来不及反馈。

### 升级降级与版本兼容
> 原文：Upgrade / Downgrade Strategy
- 已有用户升级后要做哪些改动才能保持原有行为、要做哪些改动才能用上新功能。
- 新旧组件混跑时行为如何、有什么保证；这些都要进测试计划。

### 生产就绪问卷
> 原文：Production Readiness Review Questionnaire
- 目的：上线的功能必须可观测、可扩展、可支持，出问题时能关掉或回滚。
- 开关与回滚：怎么开启/关闭？开启后会改变默认行为吗？能回滚吗？回滚后再开会怎样？有没有开关测试？
- 发布与回滚规划：发布或回滚可能怎么失败？**看哪些指标决定回滚？** 升级→降级→升级的路径测过吗？
- 监控：运维怎么知道功能在被使用？用户怎么知道它在正常工作？合理的服务目标是多少？
- 依赖、扩展性（新增调用、资源消耗）、故障排查（依赖不可用时的表现、已知故障模式、未达标时怎么定位）。

### 实施历史
> 原文：Implementation History
- 记录关键里程碑：摘要和动机合并（小组接受）、提案合并（方案达成一致）、开始实现、首个可用版本、正式发布、退役或被取代。

### 缺点与替代方案
> 原文：Drawbacks
- 缺点：为什么**不**应该做这个 KEP。
- 替代方案：考虑过哪些别的做法、为什么排除；不必像正文那么细，但要说清思路和不可接受的原因。
