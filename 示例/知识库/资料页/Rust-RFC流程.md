# Rust RFC 流程说明

> Rust 社区对「重大改动」的提案流程。特色是「最终评论期」（FCP）：决定之前给所有人一个固定的最后发言窗口。

## 要点

- 只有「重大」改动需要 RFC；重排结构、纯性能提升、用户看不到的改动不需要。
- 仓促提交的 RFC 会降低通过率：先在论坛或聊天室试水、发「预 RFC」，拿到资深成员的积极反馈再写。
- 提交后通过评论修改，**修改要新增提交、不要覆盖历史**，并在评论里说明改了什么。
- 小组成员提出「进入最终评论期」并给出处置意见（合并、关闭或推迟），全员签字后公示 10 天。
- 被接受只代表原则上同意，不代表优先级，也不代表有人会去实现。

## 逐节

### 什么时候需要RFC
> 原文：When you need to follow this process
- 需要：语言语义或语法的非修复性改动、移除语言特性、标准库的大型新增。
- 不需要：改写、重组、重构等「变形不变义」的改动；只提升客观数值指标的改动（消除警告、提速、更多平台）；只有开发者能感知、用户看不到的改动。
- 不走流程直接提交实现，可能被礼貌地要求先写 RFC。

### 写之前
> 原文：Before creating an RFC
- 仓促的 RFC 会降低通过率；低质量、提过被拒、与近期路线图不符的提议可能很快被拒，让人沮丧。
- 常见的准备：在聊天室讨论、在开发者论坛讨论、发「预 RFC」。
- 经验法则：得到长期贡献者、尤其是相关小组成员的鼓励，说明值得继续。

### 流程
> 原文：What the process is
- 复制模板 → 填写 → 提交合并请求 → 由相关小组分诊并指派负责人。
- 「动机不够有说服力、对设计影响理解不足、对缺点和替代方案不坦诚」的 RFC 通常反响不佳。
- 作者要准备好根据反馈修改；修改以新提交的形式追加，并留言说明，不要压缩或改写已公开的提交历史。
- 讨论尽量放在合并请求的评论里；线下讨论要回填摘要。
- 当权衡已经讨论充分，小组成员提出「最终评论期」动议，附处置意见（合并 / 关闭 / 推迟）。
- 不需要所有参与者达成共识（通常不可能），但支持处置意见的论证必须已经讲清，且小组外没有强烈的反对共识。
- 讨论很长的 RFC，动议前通常先发一条**总结评论**，梳理现状和主要分歧。
- 进入最终评论期前，小组全员必须签字——这往往是很多成员第一次完整细读。
- 最终评论期持续 10 个自然日，并广泛公告；多数情况下风平浪静，若出现重要新论点则取消、退回讨论。

### 生命周期
> 原文：The RFC life-cycle
- 「已接受」不是橡皮图章：仍不保证最终合入，但主要利益相关方原则上同意。
- 接受不代表优先级，也不代表有人被指派实现；作者亲自实现是推进最有效的方式。
- 接受后原则上不再大改；小修可以追加，大改应写新 RFC 并在原文加注。

### 评审
> 原文：Reviewing RFCs
- 小组可能约作者和利益相关方开会，会后把纪要贴回讨论。
- 决定做出后，如果理由在讨论中不够清楚，小组会补一条评论说明理由。

### 推迟
> 原文：RFC Postponement
- 「推迟」表示现在既不想评估也不想实现，但相信可以等。
- 被推迟的 RFC 通常已通过非正式的第一轮评估：「这类改动我们将来有可能考虑吗？」答案是否定的就该直接关闭，而不是推迟。
- 流程有意保持轻量，由共识和社区规范驱动，不强加多余结构。
