# PEP 572 · 赋值表达式（海象运算符）

> 一份真实的、争议极大但最终通过的提案。值得看的不是语法本身，而是它怎么用真实代码说服人、怎么处理反对意见、怎么记录实施中的变更。

## 要点

- 提议新增 `NAME := expr`，让赋值可以出现在表达式里。状态 Final，进入 Python 3.8。
- 「真实代码的重要性」一节专门讨论举例：玩具例子没说服力，过度复杂的例子会变成靶子。
- 例子来自标准库和作者自己的代码库，而不是为提案编出来的。
- 被否决的替代写法逐条列出，附上否决理由；常见质疑单独成节作答。
- 接受之后、发布之前的规格变动单独记录，正文与最终实现保持一致。

## 逐节

### 摘要
> 原文：Abstract
- 用 `NAME := expr` 在表达式内部给变量赋值。
- 顺带调整字典推导式的求值顺序（先算键再算值）。
- 讨论中被戏称为「海象运算符」，正式名称是赋值表达式。

### 理由
> 原文：Rationale
- 给表达式结果起名字很重要，但目前只能用语句完成，推导式等表达式场景用不了。
- 调试时可以直接在表达式里插入 `name :=` 捕获中间值，不必重构代码，降低调试时意外改坏代码的风险。

### 真实代码的重要性
> 原文：The importance of real code
- 讨论中支持者和反对者都爱用两类例子：过于简单的玩具例子、过于复杂的例子。
- 玩具例子的问题：太抽象，打动不了人；也很容易被一句「我根本不会这么写」驳回。
- 过度复杂例子的问题：给反对者送上现成的靶子（「这太晦涩了」）。
- 两类例子仍有用：用来说明语义边界。
- 要**有说服力**，例子必须来自真实代码——写的时候完全没想到这份提案。
- Tim Peters 翻了自己的代码库，结论是「适度但明确的改进」；Guido 在一个大型公司代码库里发现：程序员宁可重复计算也要少写一行。

### 实施中的规格变更
> 原文：Specification changes during implementation
- 接受之后、3.8 发布之前，根据实现经验做了两处调整，并逐条写明原因。
- 例如：放弃原先提议的专门异常类型，直接用 SyntaxError，以保持一致并避免过早锁定命名。
- 某个限制「本可以更精细」，但为纯假设的用例增加复杂度不值得，留待有充分例子时再议。

### 真实示例
> 原文：Examples from the Python standard library
- 从标准库挑了 site.py、_pydecimal.py、copy.py、datetime.py、sysconfig.py 中的片段，逐段对比改写前后。
- 另附简化推导式、捕获条件值等常见模式。

### 被否决的替代方案
> 原文：Rejected alternative proposals
- 先说明：类似提议在社区里反复出现过。
- 曾想顺带修改推导式的作用域规则，因会造成不兼容而撤回，让提案聚焦在赋值表达式本身。
- 逐条列出另外几种写法（`EXPR as NAME` 等）、只在条件语句或推导式里特殊处理、降低运算符优先级、强制加括号等，每条附否决原因。

### 常见质疑
> 原文：Frequently Raised Objections
- 为什么不直接让 `=` 变成表达式？`if (x == y)` 和 `if (x = y)` 长得像、意思完全不同，用 `:=` 区分。
- 有了赋值表达式还要赋值语句吗？两者灵活性不同，语句能 `+=`、能链式、能给属性和下标赋值。
- 为什么不用更小的作用域避免名字泄漏？早期版本这么做过，复杂度换来的收益不值，最终选择与普通赋值完全一致。

### 风格建议
> 原文：Style guide recommendations
- 语句和表达式都能用时，优先用语句，意图更清楚。
- 如果用赋值表达式会让执行顺序产生歧义，就改写成语句。
