# PEP 1 · PEP 的目的与写作指南

> Python 社区怎么提出、讨论、决定一项重大改动。整套「提案—评审—决定—存档」流程的说明书，也是本库里最完整的一份。

## 什么时候看

要设计一套提案或评审流程；想知道一份完整的提案该包含哪些部分。

## 要点

- PEP 是设计文档：既给出改动的**技术规格**，也给出**为什么这样设计**。
- 一份 PEP 只讲一个核心提议，越聚焦越容易成功；太宽会被编辑直接退回。
- 先在公开论坛试水，再找 sponsor（引路人），再提交草稿；讨论集中在一个公开帖子里。
- 最终由指导委员会（或其指定的 PEP-Delegate）拍板；被拒的提案也要留档。
- 一份成功的 PEP 有 15 个部分，其中「动机」「向后兼容」写不好会被直接拒绝。

## 逐节

### PEP是什么
> 原文：What is a PEP?
- PEP = Python Enhancement Proposal，向社区提供信息或描述新特性的设计文档。
- 应包含简明的技术规格和设计理由。
- 作者负责在社区内凝聚共识、记录不同意见。
- PEP 以文本文件形式放在版本库里，修订历史就是这份提案的历史记录。

### 三种PEP
> 原文：PEP Types
- **标准类**：新特性或新实现。
- **信息类**：讲设计问题或给出建议，不代表社区共识，读者可以不照做。
- **流程类**：改的是流程而不是语言本身，通常需要共识，读者一般不能忽略。

### 从一个想法开始
> 原文：Start with an idea for Python
- 一份 PEP 只放一个关键提议；拿不准就拆成几份。大多数改进和修复不需要 PEP。
- 每份 PEP 要有一位 champion（作者）：写文档、主持讨论、推动共识。
- 写之前先到公开论坛问「这个想法有没有被提过、被拒过」——网上搜索往往搜不全，先问能省下大量白费功夫。
- 「作者觉得好」不等于「对大多数人有用」。

### 找sponsor
> 原文：Finding a sponsor
- 初步讨论后要找一位 sponsor：核心开发者、PEP 编辑等有资格的人。
- sponsor 像导师，帮作者走完流程，之后也可以成为共同作者或决策人。

### 讨论
> 原文：Discussing a PEP
- 提交后开一个公开讨论帖，PEP 头部的 Discussions-To 指向它。
- 实质问题应在这个公开帖里谈，而不是私聊、代码评审或别的地方，避免讨论碎片化。
- 大改之后要开新帖重新征求意见，并在 Post-History 里记一笔。
- 作者负责收集反馈；为避免无休止的讨论，早期可以先找小范围专家收窄意见。

### 审议与决定
> 原文：PEP Review & Resolution
- 编辑只审格式和一致性；内容由**指导委员会**审议决定，也可委托给一位 PEP-Delegate。
- 委员会可能因利益冲突（例如与提案人同一组织）拒绝某人担任 Delegate。
- 接受的最低标准：描述清晰完整、整体是净改进、实现不会让解释器过度复杂、「足够 Pythonic」。
- 状态：Draft → Accepted → Final；另有 Provisional（暂定接受，发布后仍可撤回）、Deferred（停滞）、Rejected、Withdrawn（作者自己放弃）、Superseded、Active（长期有效的流程/信息类）。
- 被拒也要留档：「事后看不是好主意」这件事本身值得记录。
- 被接受、拒绝或撤回后，要在 Resolution 字段里贴上决定的原帖链接。
- 原文倾向于**缩小提案范围**，而不是依赖 Provisional 状态，因为后者会带来兼容性麻烦。

### 维护
> 原文：PEP Maintenance
- 定稿后 PEP 就是历史文档，不再大改；正式行为说明放到语言参考等文档里。
- 实施中根据经验调整的内容要写回 PEP，保证 Final 时与实现一致。
- 被搁置或撤回的 PEP 可以复活，但通常不如重新写一份。

### 成功的PEP包含什么
> 原文：What belongs in a successful PEP?
- 15 个部分：头部信息、摘要（约 200 词）、动机、规格、理由、向后兼容、安全影响、如何教会用户、参考实现、被否决的想法、未决问题、致谢、脚注、修订历史、版权。
- **动机**：说清现有方案为什么解决不了问题，可附上重要项目的支持；动机不足会被拒。
- **规格**：细到足以让不同团队做出互相兼容的实现。
- **理由**：为什么这样设计、考虑过哪些替代方案、其他语言怎么做；还要体现共识、回应主要反对意见。
- **向后兼容**：引入不兼容就必须写清严重程度和应对办法，写不清可直接拒。
- **如何教会用户**：给新老用户各自的学习/迁移要点。
- **参考实现**：Final 之前必须完成，但接受之前不必——「粗略共识 + 能跑的代码」有助于收敛 API 细节的争论。
- **被否决的想法**：记录被否的想法和理由，既保存思考过程，也防止同样的想法被反复提起。
- **未决问题**：草稿期还没定的事先列出来，免得别人重复讨论。
- **修订历史**：大改时按时间倒序记录，相当于提案的更新日志。
