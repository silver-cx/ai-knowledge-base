# Rust RFC 模板

> 最有特色的是把解释拆成两层：先「像已经上线一样教会别人」，再给出技术细节。还专门留了「先例」和「未来可能」两节。

## 要点

- 动机被称为「最重要的部分之一」，要有具体用例。
- 「教学式说明」：假设功能已经存在，用例子教会另一位使用者，并说明对可读性、可维护性的影响。
- 「参考级说明」：技术细节、与其他功能的交互、边界情况，并回到前面的例子逐一解释。
- 缺点、理由与替代方案、先例、未决问题、未来可能——一份 RFC 一半的篇幅在讲「为什么」和「还有什么」。

## 逐节

### 摘要
> 原文：Summary
- 一段话说清这个功能。

### 动机
> 原文：Motivation
- 任何改动都应聚焦于解决用户正在遇到的问题，要讲清问题本身和必要背景。
- 要包含几个具体用例，说明功能如何帮到用户；这些用例会反过来指导设计。
- 「这是 RFC 最重要的部分之一，可以写得很长。」

### 教学式说明
> 原文：Guide-level explanation
- 假设提议已经纳入语言，你在把它教给另一位开发者。
- 引入新的概念名称；主要靠例子来讲；说明使用者应该怎么**思考**这个功能。
- 如适用，给出示例报错信息、弃用警告、迁移指南；区分教给老用户和新用户的差异。
- 讨论对代码阅读和维护的影响——代码被读和改的次数远多于被写。

### 参考级说明
> 原文：Reference-level explanation
- 技术部分：与其他功能的交互要清楚，实现方式要大致清楚，边界情况用例子拆解。
- 要回到教学式说明里的例子，解释详细设计如何让这些例子成立。

### 缺点
> 原文：Drawbacks
- 为什么**不**应该做这件事？

### 理由与替代方案
> 原文：Rationale and alternatives
- 为什么这是所有可能设计里最好的？考虑过哪些别的设计、为什么没选？
- **不做会怎样？**
- 能否用库或宏实现而不改语言？改动让代码更好读还是更难读？

### 先例
> 原文：Prior art
- 其他语言、其他社区有没有类似做法，经验是什么，好的坏的都写。
- 相关论文或文章可以作为理论背景。
- 没有先例也没关系；但「别人有」本身不构成充分动机，Rust 有时会有意与常见做法不同。

### 未决问题
> 原文：Unresolved questions
- 哪些问题打算在 RFC 讨论中解决？哪些留到实现阶段、稳定之前解决？
- 哪些相关问题不在本 RFC 范围内，将来可以单独处理？

### 未来可能
> 原文：Future possibilities
- 这个提议自然的延伸和演化是什么，对项目整体有什么影响。
- 可以在这里「倾倒想法」；但写在这里不构成接受本 RFC 或未来 RFC 的理由。
- 想不出也可以直说想不出。
